# 为QQ Agent 0.5创作扩展

本文是创作引导的当前项目入口。用户只需复制 [AI 引导提示词](ai-extension-prompt.md)；不需要填写表单或先选择技能还是插件。AI 应先用日常语言逐步提问，复述实际需求并等用户明确确认，然后自行读取本文、[完整扩展参考](extension-reference.md)与对应的 [可执行范例](../examples/extensions/README.md)，完成制作、自检并直接放入对应文件夹，检查宿主识别且保持禁用，由用户点击启用。需要 ZIP 时另行打包，不自动上传社区。迁移旧代码时再读 [0.4 能力逐项对照](v04-extension-parity.md)。[公共SDK](plugin-sdk.md)继续保留服务边界和 UI 主题/动效合同；深度替换参考[追加式组合规格](architecture-composition.md)。不要使用0.4的`doc/extend_development`路径或旧createSkillApi示例代替当前契约。

## 从空白需求开始

第一条先问“你想让机器人学会什么？可以用一句话举个例子。”，不先展示技术方案或开始制作。后续每次只问1—3个简单问题，逐步确定使用场景、触发方式、输入、输出位置及必要的外部服务。不要让用户回答skill/plugin、API或权限名称；用户说不清时用具体例子帮助判断。对话中已有的描述只是初始想法，有内容也要澄清确认；明确回答过的事项不用重复询问。

读取开发文档和写代码之前，用短摘要复述实际需求并等待用户明确确认。用户更正后更新摘要、重新确认，不能自行把沉默或初步描述视为同意。已经确认的上下文可以沿用。确认后由AI自行定位项目、读文档和判断扩展形式；向导给出的目录可直接验证，通用提示词从AI当前工作目录及已知项目位置查找。找不到或无法区分多个安装位置时才问用户，不从data目录名称反推根目录，也不要求用户先阅读技术资料。

确认后的实施阶段继续自主完成；仅缺少必要资料、外部服务选择或出现现有公开接口无法覆盖的需求时追问。需要密钥时引导用户在本机配置，不在聊天中索取明文密钥。需要修改用户已确认的功能范围时，先更新摘要并重新确认。技术方案由AI按当前合同判断，普通包与启动覆盖层的信任边界保持不变。

## 选择扩展形式

| 需求 | 推荐入口 | 目录/清单 | 生效边界 |
| --- | --- | --- | --- |
| 模型理解用户请求后按需调用工具、执行任务或使用提示词能力 | 技能（skill） | `skills/<id>/skill.json`及`index.js` | 新功能默认禁用，用户点击启用；权限另按现有流程授权 |
| 消息事件、固定规则、定时任务或启停生命周期驱动的自动行为、后台服务 | 插件（plugin） | `plugins/<id>/plugin.json`及`index.js` | 新功能默认禁用，用户点击启用；资源随生命周期回收 |
| 注册自己的界面 | 普通扩展注册面板 | 扩展清单、入口和自有`ui/` | 面板继续运行在opaque沙箱，使用窄RPC和主题DTO |
| 更换默认页面/局部文件、后台接口、核心实现 | 管理员受信任启动覆盖层 | `overrides/<layer>/composition.json`与实现文件 | 启动时组合，需完整重启；普通市场包没有这项信任 |

技能和插件都可以注册工具或自有面板，不能只凭“有工具/有界面”分类。AI 根据已确认的主要触发方式与生命周期判断，不根据用户从技能页还是插件页复制提示词来决定。混合需求优先选择承载主要行为的形式，确实必要才拆分；有歧义时询问日常使用例子，不让用户选择技术名称。若需求实际需要替换宿主默认实现，应说明深度定制的边界，不借普通创作流程悄悄生成或启用覆盖层。

现有基本实现都是可选择的默认项。需要更换时优先追加覆盖层或包装，不直接修改出厂src/ui/bundled文件。普通扩展也不应因为需要一个自有面板就自动升级为可信覆盖层；先说明需要更换的目标及现有扩展点。

## 普通扩展

1. 选择独立小写ID；目录、清单ID和发布ID保持一致，不覆盖已有同ID扩展。
2. 清单声明`kind: skill`或`kind: plugin`、`apiVersion: 1`和`entry: index.js`。初稿和最终交付都保持`enabledByDefault: false`。即使自检通过，实际安装后的新功能仍禁用，不替用户点击启用或写入启用配置。
3. 使用当前`setup(ctx)`、工具/能力/面板注册与生命周期API。`ctx.log`是日志对象，不是0.4的日志函数；宿主不公开`ctx.kernel`。
4. 请求最小权限，配置及密钥只放自己的schema/命名空间，不复制全局模型Key、控制台令牌或其它扩展配置。修改代码后的权限决定与旧源码指纹不同，不能假设旧授权自动沿用。
5. 先在扫描目录以外完成全部文件，再将完整新目录放入目标位置。不要让逐文件写入过程暴露半份清单或入口。
6. 在技能/插件页重扫，检查清单解析、错误、禁用及权限状态；不自动批准权限。具备watcher不等于任何环境都能即时加载；明确说明实际加载证据，勿承诺“落盘必成功”。

ZIP包必须遵守现有安装器清单、路径及资源约束，不含真实配置/密钥、用户data、运行缓存或启动覆盖层。发布是独立的外部动作，生成文件、测试或本地启用不代表授权公开投稿。

需要在线更新时，按[在线更新发布说明](extension-online-updates.md)在清单声明 GitHub Releases 仓库与固定完整 ZIP 名称，保持身份和来源不变。只有用户提供或明确指定了仓库才能填写，不猜测发布位置。检查仅提示；下载替换与热加载须由用户在客户端确认。本地“重新加载”不会下载代码。

## 启动覆盖层

从`enabled: false`的独立目录开始，阅读具体目标的参数、返回值及生命周期契约。替换或包装使用对应schema版本；版本2才声明包装语义。不要把包装函数误作工厂，不在模块顶层创建不可回收的副作用。

同一目标的层按确定顺序解析；一个目标发生覆盖不意味着可以丢弃同层对其它目标的贡献。需要组合多个实现时明确依赖、顺序或包装方式，并测试重叠/不重叠、失败、撤销和默认回退。状态仓、权限和核心循环不做无协议的运行时热交换。

项目提供`node scripts/inspect-composition.mjs`时先做静态预检；它不执行代码，也不能证明真实消费者已使用新实现。启用后完整退出并重启，再验证真实调用/页面行为。移除或停用新增层并完整重启，应恢复下层或默认项。原有文件及真实数据必须保留可恢复路径。

## 验证和交付

先使用 `node scripts/extension-dev.mjs check <目录>` 做静态检查，再用 `test <目录> --case <用例文件>` 经真实加载器和 SDK 执行隔离离线用例，需要 ZIP 时再用 `pack <目录> --out <ZIP路径>` 生成包；默认直接交付完整本地目录，不要求用户下载 ZIP 再安装。完整格式与边界见[扩展参考的自检说明](extension-reference.md#13-自检打包与发布)；静态通过不表示执行通过，离线回执不表示真实 QQ 收到或社区已上架。覆盖成功、失败、并发、取消、权限/代际撤销和资源清理。界面需验证主题、窄屏、键盘、沙箱及真实交互。默认实现被替换后，要证明实际消费路径改变，而非只注册了一个名称；不相关默认能力也应保持。

测试不得实际发送QQ消息、清空真实数据、使用真实账号或自行公开发布。报告区分源码/纯函数/桩服务/真实外部服务证据，不能拿mock成功代替真实业务验收。交付列出新增文件、启用或重启步骤、实际测试结果、尚未验证项和回退方式。

创作向导只生成可复制给本机AI工具的说明；不会安装、启用、执行或发布代码。实际制作和安装由接收提示词的AI完成。读取项目位置失败时仍可复制通用提示词，需求确认后由AI自主定位，找不到才询问用户；不要从data目录名猜根目录。复制受浏览器限制时会选中文本供Ctrl+C，不能把复制失败标成成功。

本地安装检查须使用现有宿主入口，分别报告文件就位、宿主识别、禁用与权限的实际状态。最终清单仍为`enabledByDefault: false`，不写入`enabled: true`或自动批准权限。自检可以在独立临时实例中执行代码，不能因此启用用户运行中宿主的新扩展；交付时告诉用户在哪个列表找到名称并点击启用。离线加载器及受控传输测试不能替代“正在运行的宿主已加载”的证据；没有必要服务、权限或可连接宿主时，交付可安装ZIP并明确未完成的检查。不要为了让测试通过自动给新代码授权，也不要向真实QQ或收费服务发送回归请求。
