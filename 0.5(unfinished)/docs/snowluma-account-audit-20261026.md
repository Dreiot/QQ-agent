# SnowLuma 账号接入实测与修复（2026-10-26）

本次使用 Windows 上的 SnowLuma 2.2.0 完整发行包和两个真实桌面 QQ，分别核对原生进程、OneBot HTTP、WebSocket、QQA 工作区、账号记录以及浏览器中的卡片状态。真实验证在独立实例 `http://127.0.0.1:11297/` 进行，所有账号保持暂停。

## 发现与修复

| 问题 | 处理 |
| --- | --- |
| 重复接入一个已经注入的 QQ，仍重新分配端口和令牌，破坏原来的连接参数 | 读取此账号已有的 QQA 命名连接，校验后直接复用，不重复写入 |
| SnowLuma 显示进程在线，就可能被当作 QQA 已连接 | 接入时分别验证 HTTP、WS 的实际 QQ 身份；展示状态采用 QQA 账号工作区的实际连接状态 |
| 工作区注册失败被吞掉，随后在后台反复重试 | 明确返回失败状态；一次接入只注册一次，失败后等待用户显式重试 |
| 配置保存返回成功，实际保存或应用的内容却可能不一致 | 写入后读回核对；失败或接入超时时尝试恢复本次修改的命名连接。其他程序新增的连接保留；并发改动过同名连接时停止覆盖并提示检查 |
| SnowLuma 2.2 保存时省略旧版 `enabled` 字段，并补入 HTTP 默认字段 | 按实测的规范化格式比较，兼容省略默认值，避免错误地判断保存失败或改写正常连接 |
| DLL 已注入但管道断开时，QQA 无法选择恢复 | 对重新确认过 PID 和 QQ 身份的进程调用原生 `refresh`，避免重复注入 |
| 账号注册、连接或断开时清单保存失败，内存中却留下新状态 | 恢复原账号记录和连接意图；修正失败队列阻断后续操作的问题，允许存储恢复后继续操作 |
| 状态读取和接入核验并发，可能重复注册；关闭窗口后旧任务仍可能被新窗口接续 | 串行核验同一接入目标，关闭或重新打开窗口时丢弃旧的待提交目标 |
| 短暂读取失败后，旧卡片仍容易被理解为当前成功状态 | 独立刷新账号状态，标记“状态待确认”，阻止依据旧状态发起新接入，保留已有账号的断开入口 |
| 状态读取反复创建验证 WS，可能再次触发原生连接事件 | 正常应用直接读取账号工作区状态；独立使用的适配器不订阅自身探测产生的连接事件，避免刷新反馈循环 |

QQA 接入时只写入 `qq-agent-http` 和 `qq-agent-ws` 两个命名连接；不改动上游程序、首次协议确认或管理密码。

## 真实双账号结果

账号以尾号区分：A 为 7058，B 为 8561。

| 操作 | 结果 |
| --- | --- |
| 两个真实 QQ 同时接入 | 两个独立工作区；HTTP、WS 都返回各自身份，均保持暂停 |
| 关闭 A、再连接 A | B 始终保持连接；A 恢复后端口及令牌指纹保持不变 |
| 关闭 B、再连接 B | A 始终保持连接；B 恢复后端口及令牌指纹保持不变 |
| 顶部切换 A / B | 页面保持在设置页；当前查看标记与账号一致 |
| A 的“所有群统一档位”改为否，查看 B | B 仍为是；来回切换及重启后仍分别保留 |
| 开启随应用恢复、关闭 B、重启 QQA | SnowLuma 原生进程确实重启；A 恢复，B 保持关闭，未被意外补连 |
| 重新启用 B，再次重启最终版本 | 两个账号恢复连接；账号工作区 ID、清单数量和连接参数均稳定 |
| 测试收尾 | 将 A 的聊天选项恢复原值；两个账号已连接、已暂停 |

修复后的九个关键状态快照已作程序化交叉核对。关闭卡片断开的是该 QQ 的 QQA 工作区；共享 SnowLuma 的原生监听仍保留，因此另一账号无需重新启动协议端。
