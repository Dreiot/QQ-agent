# 技能与插件的在线更新

QQA 将“检查更新”和“重新加载”分开。检查只读取公开的发行信息，不下载或执行新版；用户在更新窗口确认后，才下载完整 ZIP、替换本地目录并重新加载。无更新来源的扩展继续保留本地重新加载。

设置中的“自动重新加载本地改动”只监听磁盘文件，不负责联网下载。在线版本检查由独立的 `console.extensionUpdates` 控制器提供，可通过可信启动组合替换，普通扩展不会取得更新其他扩展的宿主能力。

## 作者把文件放在哪里

使用自己的 GitHub 公开仓库和 Releases，无需另外租服务器。源码放在仓库；供 QQA 安装的完整 ZIP 上传为 Release 的附件。QQA 不会拿 GitHub 自动生成的 Source code ZIP 作为发行包。

在 `skill.json` 或 `plugin.json` 中加入：

```json
{
  "id": "my-extension",
  "kind": "skill",
  "version": "1.0.0",
  "apiVersion": 1,
  "entry": "index.js",
  "enabledByDefault": false,
  "update": {
    "type": "github",
    "repo": "YOUR-NAME/YOUR-REPOSITORY",
    "asset": "my-extension.zip"
  }
}
```

`repo` 换成自己的仓库，`asset` 是每次发行都保持一致的完整 ZIP 文件名。插件的 `kind` 使用 `plugin`，清单文件名使用 `plugin.json`。每个发行包只含一个技能或插件；可以共用一个仓库，但各自附件名需不同，版本应与该仓库 Release 的标签一致。

发布新版的步骤：

1. 修改代码，把清单版本改成例如 `1.1.0`；保持 ID、类型、仓库和 ZIP 文件名不变。
2. 使用项目工具检查与打包：`node scripts/extension-dev.mjs check <扩展目录>`，通过后执行 `node scripts/extension-dev.mjs pack <扩展目录> --out <输出目录>/my-extension.zip`。
3. 在 GitHub 创建正式 Release，标签填写 `v1.1.0`，写更新说明，上传 `my-extension.zip` 后发布。不要勾选预发布，也不要仅保存草稿。
4. ZIP 根目录应直接包含清单、入口和实际依赖文件，不能再套一层仓库文件夹。不要打包真实密钥、用户数据、运行缓存、`node_modules` 或启动覆盖层；现有安装器仍执行 8MB 压缩包、32MB 解压后等检查。

本版本对接 GitHub 的最新正式发行版，要求 `x.y.z` 语义版本号，支持 `v` 前缀；不跟踪分支提交、草稿、预发布或私有仓库，不在更新来源中保存 GitHub Token。GitHub 返回 SHA-256 时会校验下载内容。

## 使用者怎么更新

QQA 启动后检查有来源的用户扩展，之后按六小时间隔检查；新增或重新加载扩展后会重新安排检查，同一版本的检查结果有缓存。检查失败可点“检查更新”立即重试。页面空闲时不轮询状态，由实时事件更新提示。

发现新版后，工作台弹出提醒，技能或插件卡片显示新版号和“更新”。打开后可查看当前版本、新版号、仓库和作者说明；按“下载并更新”才会开始下载。取消、关闭窗口和仅检查均不会下载新版。

设置及 SDK 存储命名空间保留。启用的扩展成功替换后热加载，停用的扩展保持停用且不执行入口。新版身份、类型、版本和来源必须与用户确认的信息一致；源代码指纹改变后的宿主授权仍需重新确认。

下载、校验、解包失败均不替换原目录；新版加载失败则恢复原目录并重新加载。成功更新的原版保留在当前扩展根目录下 `.extension-management-v1/backups/`。更新时同一扩展的启停、卸载及手动重新加载会暂时拒绝，其他扩展仍可使用。

## 更新来源不适用的情况

没有 `update` 字段或字段无效时，仅保留本地“重新加载”，不会猜测下载位置。内置默认能力随 QQA 更新；可信启动覆盖层仍需完整重启，不通过普通扩展更新包替换核心。
